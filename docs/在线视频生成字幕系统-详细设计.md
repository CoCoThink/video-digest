## 1. 概述

本文档给出需求 v1.5 的实现级设计：进程模型、模块划分、数据结构、接口细节、前端提取实现与异常处理。所有取舍延续需求 §2.4「实现简单优先」：单一模型、单一提取路径（统一 MKA）、无数据库（文件系统即状态）、HTTP 轮询。

### 1.1 关键设计决策汇总

| # | 决策 | 理由 | 对应需求 |
|---|---|---|---|
| D1 | 后端 = **API 进程 + 1 个常驻 GPU Worker 子进程**（stdlib `multiprocessing`，spawn） | 超时可 `kill` 强制回收 GPU（线程杀不掉挂死的 CUDA 调用）；OOM/驱动异常只需重启子进程，API 进程不受影响；模型仍常驻（驻留在子进程内，启动加载一次） | FR-B2 超时、FR-B3 常驻、R4 |
| D2 | Web 框架 FastAPI + uvicorn 单进程；前端为**无构建**静态页（原生 JS） | 最少依赖，一条 `uvicorn` 命令起服务并顺带托管静态页，同源免 CORS | §2.4 |
| D3 | 队列 = API 进程内 `deque`；任务状态 = 每任务目录下一个 `status.json`（原子写） | 无数据库；重启后队列丢失、产物保留，与 FR-B7 语义一致 | §2.4-3、FR-B2/B7 |
| D4 | ffmpeg.wasm 0.12.x **单线程 core**，输入文件经 **WORKERFS 挂载**（不整体复制进 wasm 内存） | 单线程 core 不需要 SharedArrayBuffer/COOP/COEP 响应头，部署零门槛；WORKERFS 使 GB 级视频不受 wasm 内存限制；stream copy 本身是 I/O 型操作，单线程足够快 | FR-F2、NFR-4 |
| D5 | 后处理在 Worker 内**串行**执行（不与下一任务 GPU 转写并行） | 后处理 ≤ 5 s，占总时长 < 2%；省一套并行调度。需求 FR-B5 用词为「可并行」非「必须」，按 §2.4 从简 | FR-B5、§2.4 |
| D6 | 删除任务时保留一个**墓碑** `status.json`（`state=deleted`，产物全删） | 「访问已删除结果」需返回明确的"已删除"提示而非 404（验收 6/7） | FR-B7、验收 6/7 |
| D7 | 新增 `GET /api/config` 接口 | FR-F4 要求 RTF「服务端配置下发」，FR-F3 要求前端上传前预判大小上限，需要一个只读配置接口 | FR-F4/F3（需求允许接口在设计阶段细化） |
| D8 | 历史列表用**服务端目录扫描**（`GET /api/tasks`），非浏览器 localStorage | 真相在磁盘 `status.json`（D3 文件系统即状态）；服务端列表天然对清缓存/换浏览器/换设备鲁棒，且无需在前端再维护一份可能与磁盘不一致的任务索引 | FR-F8 |
| D9 | 单任务内用**容量 1 的 GPU ASR / CPU 对齐两级流水线** | qwen-asr 0.0.6 原实现先全量 ASR、再全量对齐；本项目 batch=1，两段逐块调用可等价重排。GPU 跑第 i+1 块时 CPU 对齐第 i 块，不增加显存；容量 1 防止长音频积压 | FR-B3/B4、NFR-1 |
| D10 | FireRed 首期采用**启动级 backend 切换**，不做单任务模型切换；Qwen 仍为默认 | 4 GB GPU 无法同时常驻两套模型；逐任务卸载/重载会放大时延、主机内存峰值和 CUDA 失败面。Worker 启动时按 `VD_ASR_BACKEND` 只加载一个 backend，保持 D1 单 Worker 与 D3 任务模型不变 | NFR-1/NFR-4、§2.4 |

### 2.1 架构图

```

│  │ 本地视频文件  │ ────────────────→ │ ffmpeg.wasm(单线程) │      │
│  └──────────────┘  (视频不出本机)    │ -vn -c:a copy       │      │
│                                      │ → out.mka (内存Blob) │      │
│                                      └─────────┬──────────┘      │
└────────────────────────────────────────────────┼─────────────────┘
                     HTTP(同源)                   │ 仅音频上传
┌────────────────────────────────────────────────▼─────────────────┐
│  API 进程（FastAPI + uvicorn，不触碰 CUDA）                       │
│  ・路由：上传/列表/状态/下载/删除/配置/健康 ・静态页托管          │
│  ・上传校验：内容嗅探 + ffprobe（时长/音轨/可解码）               │
│  ・内存队列 deque + 调度线程（dispatcher）                        │
│  ・任务目录读写：data/tasks/{task_id}/status.json                 │
└───────────────┬──────────────────────────────────────────────────┘
                │ multiprocessing.Queue（只传 task_id）
                │ 超时 → kill + respawn
┌───────────────▼──────────────────────────────────────────────────┐
│  GPU Worker 子进程（常驻，启动时加载模型一次）                    │
│  ffmpeg→16k WAV → ASR(int8-1.7B,GPU) ∥ 上一块对齐(0.6B,CPU)     │
│  → items.json → 标点断句 → 排版规范化 → SRT/TXT                  │
│  状态推进直接写 status.json                                       │
└──────────────────────────────────────────────────────────────────┘
```

| 层 | 选型 | 版本/说明 |
|---|---|---|
| 服务框架 | FastAPI + uvicorn | 单 uvicorn 进程；`StaticFiles` 托管 `web/`，同源部署免 CORS |

| ASR | qwen-asr 0.0.6 + transformers 4.57.x + bitsandbytes | 实测环境为准（NFR-4）；mamba env `qwen-asr`，Python 3.11 |
| 音频处理 | ffmpeg 8.x（服务端 CLI）、ffprobe | 子进程调用，不用 python 绑定 |
| 后处理 | 复用 `build_srt_punct.py` / `build_srt_layout.py` 逻辑 + jieba | 重构为可 import 的模块，CLI 入口保留 |
| 前端 | 原生 HTML/JS/CSS，无框架无构建 | 单页 `index.html`；`?task=` URL 参数恢复 + 首页「历史任务」列表（§7.5） |
| 浏览器提取 | @ffmpeg/ffmpeg 0.12.x + @ffmpeg/core（单线程） | **自托管**于 `web/vendor/ffmpeg/`（内网可用，不依赖 CDN） |

### 2.3 进程与线程模型

**API 进程**（不 import torch，不触碰 CUDA）：

- uvicorn 事件循环：处理全部 HTTP 请求。浏览器以 16MiB 原始二进制分块上传，服务端按偏移流式追加落盘；ffprobe 校验放在线程池执行，避免阻塞事件循环。
- **dispatcher 线程**（1 个）：循环从 `deque` 取队首任务 → 投递 `task_id` 给 Worker → 带超时等待结果 → 超时则 `kill` Worker 并 respawn → 继续下一任务。
- 队列锁：`deque` 的入队/出队/取消/查位置由一把 `threading.Lock` 保护（操作皆为微秒级，无争用问题）。

**GPU Worker 子进程**（spawn 启动；`multiprocessing.set_start_method("spawn")`，CUDA 要求）：

- 启动即加载模型（约 14 s），随后循环阻塞读任务队列；收到 `task_id` 后独立完成 预处理→转写→后处理→产物 全链，逐阶段更新该任务的 `status.json`，结束后向结果队列回报 `{task_id, ok|failed}`。
- 转写主线程独占 ASR 模型/GPU；一个 `ThreadPoolExecutor(max_workers=1)` 线程独占 CPU 对齐器。两者使用不同模型与 processor，只在主线程汇合结果并写状态。
- Worker 崩溃/被 kill 后由 dispatcher respawn（重新加载模型，仅异常场景付出 14 s 代价）。

**并发边界**：全系统同一时刻至多 1 个任务在执行（FR-B2 单 GPU 串行）；状态查询/下载是纯文件读，天然支持 ≥ 20 并发（NFR-2）。

## 4. 后端详细设计

### 4.1 任务状态机

```
                    ┌────────────→ cancelled   (DELETE，仅 queued 可达)
queued ──→ preprocessing ──→ transcribing ──→ postprocessing ──→ done ──→ deleted
   │             │                 │                 │                     (DELETE)
   └─────────────┴─────────────────┴─────────────────┴──→ failed ──→ deleted
```

| 状态 | 写入者 | 说明 |
|---|---|---|
| `queued` | API（上传成功时） | 队列位置不落盘，由 API 从内存 deque 实时计算 |
| `preprocessing` | Worker | ffmpeg 转 16k WAV |
| `transcribing` | Worker | ASR + 对齐（耗时主体） |
| `postprocessing` | Worker | 断句 + 排版 + 产物生成 |
| `done` | Worker | 产物就绪，音频已删 |
| `failed` | Worker（业务失败）/ dispatcher（超时、Worker 崩溃）/ 启动扫描（重启中断） | 带 `error{code,message}` |
| `cancelled` | API | DELETE 排队中任务 |
| `deleted` | API | DELETE 完成/失败任务；产物删除，仅留墓碑 status.json（D6） |

**status.json 原子写**：写临时文件 + `os.replace`，杜绝轮询读到半截 JSON。写入者按上表分区（同一任务同一时刻只有一个写入者），无并发写冲突。

### 4.2 调度器（scheduler.py）

```python
# dispatcher 线程主循环（伪代码）
while True:
    task_id = queue.pop_front_blocking()          # deque + condition
    task_q.put(task_id)                           # → Worker
    timeout = duration * 3 + 600                  # FR-B2 默认，可配置
    try:
        result = result_q.get(timeout=timeout)    # ← Worker
    except Empty:                                 # 超时：强制终止
        worker.kill(); worker.join()
        store.mark_failed(task_id, "TIMEOUT", "任务执行超时，已强制终止")
        worker = spawn_worker()                   # 重载模型（~14s），仅异常路径
    # result 为 ok/failed 均已由 Worker 落盘，dispatcher 不再处理
```

- **Worker 意外死亡**（非超时，如段错误）：`result_q.get` 期间轮询 `worker.is_alive()`（get 带小步长超时循环实现），发现死亡即标记当前任务 `failed(WORKER_CRASHED)` 并 respawn。
- **入队**：上传接口在校验通过后 `append`；满（≥ `queue_capacity`，默认 10，含正在执行的任务）则拒绝，返回 `QUEUE_FULL`。
- **取消**：DELETE 排队任务时从 deque 中摘除并标记 `cancelled`；正在执行的任务本期返回 409（取消运行中为 P1）。
- **启动恢复**：服务启动时扫描 `data/tasks/*/status.json`，凡处于非终态（`queued/preprocessing/transcribing/postprocessing`）一律改写为 `failed(INTERRUPTED, "服务已重启，请重新上传")`；终态任务（done/failed/cancelled/deleted）原样保留 → 已完成产物重启后仍可下载（FR-B7、验收 7）。

### 4.3 GPU Worker（worker.py）

启动序（一次性）：

```python
os.environ.setdefault("PYTORCH_ALLOC_CONF", "expandable_segments:True")
import qwen_asr.inference.qwen3_asr as _qa
_qa.MAX_FORCE_ALIGN_INPUT_SECONDS = cfg.chunk_sec   # 默认 30（4GB 卡留足单块峰值余量，见踩坑 §4.8）
_qa.MAX_ASR_INPUT_SECONDS = cfg.chunk_sec
model = Qwen3ASRModel.from_pretrained(
    cfg.asr_model_path,                 # 支持本地目录（ModelScope 预下载）
    load_in_8bit=True,
    device_map={"": 0},                 # 必须是 {"":0}，"cuda:0" 触发 bnb SCB bug（实测报告 §4.1）
    forced_aligner=cfg.aligner_model_path,
    forced_aligner_kwargs={"device_map": "cpu", "dtype": torch.float32},
)
```

任务循环（每任务）：

1. `preprocessing`：`ffmpeg -y -i upload.bin -vn -ac 1 -ar 16000 -c:a pcm_s16le audio_16k.wav`（全链路唯一一次重采样，FR-B1）。
2. `transcribing`：`asr.transcribe(model, audio_16k.wav, language=None)`；产出带标点全文 + 逐 token 时间戳，落盘 `items.json`。
   - **流水线编排**：复用 qwen-asr 的 `normalize_audios` / `split_audio_into_chunks` / `parse_asr_output` 以及模型的偏移、合并方法。主线程逐块 `_infer_asr`；每块 ASR 后先汇合上一块对齐，再向单 CPU 线程投递当前块。始终至多一个对齐任务在途，最后显式排空。
   - **语义等价**：本项目 `max_inference_batch_size=1`，故每次 ASR/对齐输入与上游串行路径相同；静音文本仍跳过对齐，时间戳仍按块偏移后顺序合并。
   - **OOM 自愈**（R4）：捕获显存不足 → `torch.cuda.empty_cache()` → 原参重试 1 次 → 仍失败标记 `failed(GPU_OOM)`。注意 4GB 卡越界抛的是**普通 `RuntimeError`**（"CUDA driver error: out of memory"）而非 `torch.cuda.OutOfMemoryError`，故按异常消息兜底识别（`asr._is_oom` / `worker._classify`，见踩坑 §4.8）。
3. `postprocessing`：`punct.py`（断句）→ `layout.py`（min-dur 1.0 / max-dur 7 / cps 9 / line-width 18 / merge-below 4 / jieba + 拉丁 token 保护 / 消重叠，参数取自配置）→ `subtitle.py` 写 `subtitle.srt`、`transcript.txt`。
4. 收尾：删除 `upload.bin`、`audio_16k.wav`（FR-B7）→ 状态 `done` → 回报结果队列。
5. 任一阶段异常：捕获、写 `failed{code,message}` 与 `task.log` 堆栈、**同样删除音频文件**、回报 failed。

**分块级进度（P1，已实现）**：项目侧显式编排已知总块数 N，以 `N` 次 ASR + 至多 `N` 次对齐为分母；主线程每完成/汇合一步把 1–99 的 `progress_percent` 写入 `status.json`。进度随流水线交错上升，不再先冲到 50% 再进入对齐；静音块不虚构对齐工作量，所以尾值可能低于 99%，随后正常进入 `postprocessing`。首块前仍为 `null`，前端显示不确定动画。

### 4.4 上传校验（probe.py，API 进程内）

按序执行，先廉价后昂贵，任一失败即拒绝并删除已落盘文件：

1. `POST /api/uploads` 校验声明总大小和容量，生成 upload_id（同时作为最终 task_id）及空的 `upload.bin`。
2. `PUT /api/uploads/{id}` 按 `Upload-Offset` 流式追加原始二进制分块；单块默认不超过 16MiB，总量不得超过声明值和 `max_size_bytes`。偏移冲突返回 409，本次写入异常则回滚。
3. `POST /api/uploads/{id}/complete` 校验实际大小等于声明值，再执行 `ffprobe -v error -print_format json -show_streams -show_format upload.bin`（内容嗅探，不信任扩展名/Content-Type）：
   - 无音频流 → `NO_AUDIO_STREAM`；
   - 探测失败/不可解码 → `DECODE_FAILED`；
   - `duration` 为 0 → `EMPTY_AUDIO`；超 `max_duration_sec`（默认 3 h）→ `DURATION_EXCEEDED`。
4. 通过 → 写 `status.json(queued)`、入队、返回 201；完成接口幂等，响应丢失后可安全重试。

## 5. 数据设计

### 5.1 task_id

`secrets.token_urlsafe(16)` → 128 bit 随机、URL 安全、不可猜测（NFR-5）。同时作为目录名（字符集天然安全，无路径穿越风险；仍在读取侧做白名单正则校验 `^[A-Za-z0-9_-]{16,32}$`）。

### 5.2 status.json Schema

```json
{
  "task_id": "kJ8fQ2xL9mNpR4sT7vWy0A",
  "state": "transcribing",
  "original_filename": "讲座.mkv",
  "audio_duration_sec": 606.3,
  "audio_size_bytes": 10485760,
  "created_at": "2026-07-15T10:00:00+08:00",
  "updated_at": "2026-07-15T10:03:20+08:00",
  "finished_at": null,
  "progress_percent": null,
  "stages": {
    "preprocessing":  {"started_at": "...", "ended_at": "...", "elapsed_sec": 2.1},
    "transcribing":   {"started_at": "...", "ended_at": null,  "elapsed_sec": null},
    "postprocessing": null
  },
  "error": null,
  "artifacts": []
}
```

- `error`：失败时为 `{"code": "TIMEOUT", "message": "任务执行超时，已强制终止"}`。
- `artifacts`：`done` 后为 `["srt", "txt"]`（P1 加 `"vtt"`、`"raw_srt"`），前端据此渲染下载按钮。
- `stages` 各阶段耗时兼作任务级可观测性数据（NFR-6 的 P0 部分）。
- 队列位置**不在此文件**：由 API 进程从内存 deque 计算，随 GET 响应动态返回。
- 删除后的墓碑仅保留：`task_id / state="deleted" / original_filename / created_at / updated_at`。

## 6. API 详细设计

通用约定：错误响应统一为 `{"error": {"code": "...", "message": "..."}}`；message 为可直接展示给用户的中文。

### 6.1 `/api/uploads` — 分块上传并创建任务

- `POST /api/uploads`：JSON `{"filename":"原视频名","size":完整音频字节数}`，成功 `201` 返回 `{upload_id,chunk_size,received_size}`。
- `PUT /api/uploads/{id}`：请求体为原始二进制，请求头 `Upload-Offset` 为本块起始偏移；成功返回最新 `received_size`。
- `GET /api/uploads/{id}`：查询服务端已接收偏移，供网络中断后续传。
- `DELETE /api/uploads/{id}`：取消并删除未完成上传。
- `POST /api/uploads/{id}/complete`：完整性及音频内容校验后入队，成功 `201`：

```json
{"task_id": "kJ8f...", "state": "queued", "queue_position": 3,
 "audio_duration_sec": 606.3, "estimated_process_sec": 394}
```

- 失败：`409 UPLOAD_INCOMPLETE / UPLOAD_OFFSET_MISMATCH`、`429 QUEUE_FULL`、`413 SIZE_EXCEEDED / UPLOAD_CHUNK_TOO_LARGE`、`422 NO_AUDIO_STREAM / DECODE_FAILED / EMPTY_AUDIO / DURATION_EXCEEDED`。

### 6.2 `GET /api/tasks` — 历史任务列表（FR-F8、D8）

- 查询参数：`include_deleted`（默认 `false`，为 `true` 时含 `deleted` 墓碑）。
- 实现：扫描 `data/tasks/*/status.json`，取轻量摘要字段，按 `created_at` **倒序**（同为 `+08:00` ISO，字典序即时间序；缺失回退 `updated_at`），默认跳过墓碑；上限 200 条。`queued` 任务附动态 `queue_position`（同 §6.3，由内存 deque 计算）。
- `200`：

```json
{"tasks": [
  {"task_id": "kJ8f...", "state": "done", "original_filename": "讲座.mkv",
   "audio_duration_sec": 606.3, "created_at": "2026-07-16T10:00:00+08:00",
   "updated_at": "...", "finished_at": "...", "error": null, "queue_position": null}
]}
```

- 仅返回列表渲染所需字段（不含 `stages`/`artifacts` 等重字段）；前端据此渲染首页历史列表，点选即恢复（§7.5）。

### 6.3 `GET /api/tasks/{id}` — 查询状态（轮询）

- `200`：status.json 内容 + 动态字段 `queue_position`（非 queued 为 null）。
- `404 TASK_NOT_FOUND`（含 id 格式非法）。注意 `deleted` 状态返回 200 + `state:"deleted"`（前端据此提示"结果已删除"，验收 6）。

### 6.4 `DELETE /api/tasks/{id}` — 取消 / 删除

| 当前状态 | 行为 | 响应 |
|---|---|---|
| `queued` | 出队，状态 → `cancelled` | `200 {"state":"cancelled"}` |
| 运行中三态 | 本期不支持取消运行中（P1） | `409 TASK_RUNNING` |
| `done` / `failed` / `cancelled` | 删产物与日志，留墓碑，状态 → `deleted` | `200 {"state":"deleted"}` |
| `deleted` | 幂等 | `200 {"state":"deleted"}` |

### 6.5 `GET /api/tasks/{id}/result?format=srt|txt` — 下载产物

- `200`：文件流。`Content-Disposition: attachment; filename*=UTF-8''<原视频名去扩展名>.srt`（FR-F6 文件名沿用）。
- `404 RESULT_NOT_READY`（未完成）、`410 TASK_DELETED`（已删除）、`400 BAD_FORMAT`。
- P1 扩展 `format=vtt|raw_srt`。

### 6.6 `GET /api/config` — 前端配置下发（D7）

```json
{"rtf": 0.65, "max_duration_sec": 10800, "max_size_bytes": 209715200,
 "queue_capacity": 10, "accepted_note": "任意 ffmpeg 可解码音频"}
```

### 6.7 `GET /api/health` — 健康检查（P1）

```json
{"status": "ok", "model_loaded": true, "worker_alive": true,
 "queue_depth": 2, "current_task_id": "kJ8f..."}
```

### 6.8 错误码总表

| code | HTTP | 场景（对应 FR-F7） | 前端提示要点 |
|---|---|---|---|
| `QUEUE_FULL` | 429 | 队列已满 | 稍后重试，无需重新提取 |
| `SIZE_EXCEEDED` | 413 | 音轨超大小上限 | 提示上限值；FLAC/PCM 场景见 R3 |
| `DURATION_EXCEEDED` | 422 | 超时长上限 | 提示上限值 |
| `NO_AUDIO_STREAM` | 422 | 无音轨 | 明示"文件不含音频" |
| `DECODE_FAILED` | 422 | 损坏/不可解码 | 附自助 ffmpeg 命令（FR-F2） |
| `EMPTY_AUDIO` | 422 | 时长为 0 | — |
| `TASK_NOT_FOUND` | 404 | 任务不存在 | — |
| `TASK_RUNNING` | 409 | 删除运行中任务 | — |
| `RESULT_NOT_READY` | 404 | 产物未就绪 | — |
| `TASK_DELETED` | 410 | 访问已删产物 | 明示"已被删除" |
| `TIMEOUT` / `GPU_OOM` / `WORKER_CRASHED` / `INTERRUPTED` / `INTERNAL` | (随 GET 状态返回) | 任务失败原因 | 展示 message，建议重传 |

## 7. 前端详细设计

### 7.1 页面状态机（app.js 单一状态变量驱动渲染）

```
idle（选择文件 + 首页「历史任务」列表，见 §7.5）
  → extracting（ffmpeg.wasm 解封装，纯音频文件跳过本态）
  → uploading（XHR 分块进度条，可取消；失败同步服务端偏移后续传，Blob 留存内存）
  → queued（显示队列位置）
  → processing（阶段文案 + 剩余时间 = duration×RTF − 已耗时）
  → done（预览 + 下载 + 删除按钮）
  | error（错误文案 + 恢复动作）
```

- 进入 `queued` 即把 `?task=<id>` 写入 URL（`history.replaceState`）并在页面明示 task_id；打开带 `?task=` 的 URL 直接进入轮询流程（FR-F5 恢复）。
- 轮询：`GET /api/tasks/{id}`，固定 2 s 间隔（接口为纯文件读，开销可忽略；不做退避，从简）。
- 无 `?task=` 参数进入 `idle` 时加载历史列表（§7.5）；从历史/URL 恢复任务复用同一入口 `openTask(id)`：写 `?task=` → `show(progress)` → 启动轮询，`done/failed/…` 均由轮询渲染分支处理。

### 7.2 音轨提取（核心：ffmpeg.wasm 单线程 + WORKERFS）

```js
const ffmpeg = new FFmpeg();
await ffmpeg.load({ coreURL: "/vendor/ffmpeg/ffmpeg-core.js" });   // 自托管，单线程 core
await ffmpeg.createDir("/in");                                   // 初始化时只创建一次

async function extractAudio(file) {
  await ffmpeg.mount("WORKERFS", { files: [file] }, "/in");        // 不复制整个视频进内存
  try {
    await ffmpeg.exec(["-i", `/in/${file.name}`,
                       "-map", "0:a:0",            // 默认第一条音轨（FR-F2）
                       "-vn", "-c:a", "copy",      // 只解封装，比特级无损
                       "-f", "matroska", "/out.mka"]);
    const data = await ffmpeg.readFile("/out.mka"); // 音轨体积远小于视频，MEMFS 可承受
    return new Blob([data.buffer], { type: "video/x-matroska" });
  } finally {
    try { await ffmpeg.unmount("/in"); } catch (_) {}
    try { await ffmpeg.deleteFile("/out.mka"); } catch (_) {}
  }
}
```

- **单线程 core 的部署意义**：多线程 core 依赖 SharedArrayBuffer，要求服务端下发 COOP/COEP 头且限制第三方资源；单线程免除全部要求，仅需 WebAssembly（NFR-4）。stream copy 不做编解码，单线程速度足够（I/O 型）。
- **挂载点生命周期**：`/in` 在 ffmpeg worker 初始化时只创建一次；每次提取仅挂载、卸载 WORKERFS。`unmount` 只解除文件系统挂载，不删除挂载点目录，不能在下一次提取时重复 `createDir("/in")`。
- **时长获取**：解析 ffmpeg log 事件中的 `Duration: HH:MM:SS.xx` 行，用于选择后展示（FR-F1）与本地预估；服务端 ffprobe 结果为权威值。
- **提取进度**：解析 log 中 `time=` 对照 Duration 计算百分比。
- **纯音频文件**：按扩展名白名单（wav/mp3/m4a/aac/flac/ogg/oga/opus/mka）跳过提取直接上传（FR-F1）；判断错误无害——后端内容嗅探兜底。
- **失败处理**（R1）：`exec` 返回非 0 或抛异常 → 展示错误 + 自助方案文案：`可在本机执行 ffmpeg -i 视频 -vn -c:a copy 音频.mka 后，将生成的音频文件直接上传`。不实现解码兜底（§2.4）。
- **上传前预检**：产物大小对照 `/api/config` 的 `max_size_bytes`，超限直接本地提示（R3），不发无效请求。

### 7.3 上传

- 先 `POST /api/uploads` 初始化，再用 `XMLHttpRequest` 逐个 PUT 原始二进制分块（`upload.onprogress` 计算整体进度），最后调用 `complete`。
- 默认分块 16MiB；Cloudflare 返回 413 时逐级减半，最低 1MiB。
- 请求失败先 GET 会话同步 `received_size`，避免响应丢失造成重复写入；自动重试后仍失败则显示“重试上传”。取消会 `xhr.abort()` 并 DELETE 会话。

### 7.4 结果预览、下载与删除

- 预览：`GET result?format=srt` 文本，前端以正则按 cue 块解析（序号/时间轴/文本），渲染"时间 + 文本"列表（FR-F6）。
- 下载：`<a href="/api/tasks/{id}/result?format=srt" download>`，文件名由服务端 Content-Disposition 决定。
- 删除：按钮 → `confirm()` 二次确认 → `DELETE` → 成功后页面转"已删除"终态。

### 7.5 历史任务列表（FR-F8、D8）

- 位置：`idle` 卡片内、选择框下方的「历史任务」区，含手动刷新按钮。进入 `idle`（首屏无 `?task=`、或点「处理新文件」返回）时调 `loadHistory()`：`GET /api/tasks` → 逐条渲染；列表为空则隐藏该区。
- 条目：原文件名 + 状态徽章（`已完成`绿 / 进行中蓝 / 其它灰）+ 元信息（创建时间 `MM-DD HH:mm`、时长，排队中附队列位置）+ 删除按钮（`✕`）。
- 交互：
  - 点条目 → `openTask(task_id)`（§7.1），复用 `?task=` 恢复路径。
  - 点 `✕` → `event.stopPropagation()` 阻止触发条目恢复 → `confirm()` → `DELETE` → `loadHistory()` 刷新。
- 数据一律来自服务端（D8），不落 localStorage；因此清缓存/换浏览器/换设备都能找回，且不会与磁盘状态不一致。
- 列表状态为拉取瞬时快照，不做常驻轮询；进行中任务的实时进度在点入后由 §7.1 轮询呈现，列表侧用刷新按钮按需更新。

```
用户          浏览器(app.js)                API进程                    Worker子进程
 │ 选择视频 →  │
 │             │ WORKERFS挂载+exec(-c:a copy)

 │             │ ──── PUT chunks(offset) ────→ │ 按偏移流式落盘
 │             │ ──── POST complete ─────────→ │ 完整性+ffprobe校验/入队
 │             │ ←─ 201 {task_id,估时} ─────── │ status=queued
 │             │ (URL写入?task=id)             │
 │             │                               │ dispatcher: task_id ─────→ │ status=preprocessing
 │             │ ── GET /api/tasks/id ──(2s)─→ │ 读status.json              │ ffmpeg→16k wav
 │             │ ←─ {state,queue_position} ─── │                            │ status=transcribing
 │             │        ……轮询……               │                            │ ASR+对齐→items.json
 │             │                               │                            │ status=postprocessing
 │             │                               │                            │ 断句→排版→srt/txt
 │             │                               │                            │ 删音频, status=done
 │             │ ←─ {state:done,artifacts} ─── │ ←──── result: ok ───────── │
 │ 预览/下载 ← │ ── GET result?format=srt ───→ │ 文件流
```

## 10. 日志与可观测性

- **任务日志** `task.log`：各阶段起止与耗时、音频时长、转写字数、显存峰值（`torch.cuda.max_memory_allocated`）、失败堆栈。不含音频内容（FR-B7）。

## 11. 安全设计（NFR-5）

- task_id 128 bit 随机（§5.1），读取侧正则白名单防路径穿越。
- 上传内容嗅探（§4.4），不执行、不解析用户文件内容（仅 ffmpeg/ffprobe 处理）。
- 服务以非特权用户运行；`data/` 目录权限 700。
- 下载响应固定 `Content-Type: application/octet-stream` + attachment，防内容嗅探型 XSS；预览渲染用 `textContent` 赋值（不 innerHTML）。
- 不做账号鉴权（内网定位）；公网暴露须在反向代理层加访问控制（部署文档说明）。
