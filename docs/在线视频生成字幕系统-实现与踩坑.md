## 1. 实现结构（落地版）

代码见 `server/`（后端，Python）与 `web/`（前端，无构建原生 JS），另见 `server/README.md` 的运行说明。

```
server/                    API 进程不 import torch、不碰 CUDA
├── main.py                FastAPI 七接口（含 GET /api/tasks 历史列表）+ 静态托管 + no-cache 中间件
├── config.py              VD_ 前缀配置
├── store.py               task_id / status.json 原子写 / 启动恢复 / 删除墓碑 / list_tasks 列表摘要
├── scheduler.py           deque + dispatcher 线程 + Worker spawn/kill/respawn/超时
├── worker.py              GPU Worker 子进程入口（顶层 torch-free，常驻模型 + 任务循环）
├── probe.py               ffprobe 上传校验
├── errors.py              API 错误码目录
└── pipeline/              preprocess / layout / subtitle / punctuation
    ├── asr.py             backend factory + Qwen 流水线兼容层
    └── backends/          base / qwen / firered / funasr / wav_chunks
web/
├── index.html app.js style.css
└── vendor/ffmpeg/         自托管 ffmpeg.wasm（含一处补丁，见 §4.7 与该目录 README）
```

关键结构决策沿用设计 §1.1：**API 进程 + 1 个常驻 GPU Worker 子进程**（解决“模型常驻”与“超时强杀”矛盾、隔离 OOM/驱动异常）、文件系统即状态（无数据库）、浏览器内无损提取音轨（视频不出本机）。Worker 启动时只加载 Qwen、FireRed 或 FunASR 中的一种，默认 Qwen，不提供逐任务切换。

## 2. 验收结论（实测）

| 验收 | 结论 | 证据 |
|---|---|---|
| 1 一致性 | **通过**（后处理逐字节一致） | 用服务自身产出的 `items.json` 跑独立脚本 `build_srt_layout.py`，SRT 与服务 `subtitle.srt` **byte-identical**；转写正文与实测参照去标点后相似度 **98.66%** |
| 2 无损提取 | **通过**（真实浏览器验证） | 浏览器 ffmpeg.wasm 提取出的音轨，其音频码流 SHA256 与源文件**完全一致**（`-f streamhash -hash sha256`） |
| 3 性能 | **通过** | 原验收 606s 样本 ≈ **6.4 min ≤ 8 min**；流水线 A/B 的 120s/4 块样本由 **119.366s → 84.337s（1.415x）**，峰值分配显存 2.680→2.626GB |
| 4 质量 | **通过** | 无 <1s / >7s cue，无 >9.5 cps，最长行 19 字符 |
| 5 排队 | **通过** | A 运行时 B 得 `queue_position=2`，串行执行；取消排队任务→`cancelled`；满 10 个第 11 个→`QUEUE_FULL` |
| 6 边界 | **通过** | API 错误码与 Worker 失败分类实测（见 §5） |
| 7 清理与保留 | **通过** | done 后无 `upload.bin`/`*.wav`；重启后中断任务→`failed(INTERRUPTED)` 且音频已删、完成任务墓碑存活；删除留 222B 墓碑 |
| 8 语言 | **通过** | `language=None` 自动判定，实测中英混合视频识别为"中英混合"并正确转写 |
| 9 多 backend 契约 | **通过（代码与烟雾试验）** | 三 backend factory、上下文、低能量切块、FireRed 异常恢复和公共输出校验纳入 37 项自动测试；Qwen 30 秒 API 烟雾测试通过 |
| 10 FunASR 稳定准入 | **未通过，保持实验级** | 180 秒 GPU 试验 RTF 0.122、峰值 3.755GB；尚缺 20–50 个代表性文件、人工真值、小时级 OOM 与许可审查 |

> `layout.align_chars()` 没有完整复刻对齐器的 Unicode 清洗规则，遇到 `A.I.`
> 等未列入固定标点表的符号后永久失步。修复后 157.6 分钟样本的 37,784 个
> 对齐字符全部进入字幕，时间轴覆盖到 `02:37:36`。详见 §4.10。

## 3. 端到端验证方法（可复现）

后端（curl）：起服务 → `POST /api/uploads` 初始化 → 按偏移 `PUT` 音频分块 → `POST .../complete` → 2s 轮询 `GET /api/tasks/{id}` 到 done → `GET .../result?format=srt|txt` 下载。

前端（**必须用真实浏览器**，见 §6 教训）：用 Playwright + 真实 Chromium 驱动页面，捕获 `console`/`pageerror`，断言"提取产物比特级一致 + 全流程到 DONE"。无 sudo 装 Chromium 依赖库的办法：

```bash
# headless-shell 缺 libnspr4/libnss3/libnssutil3/libasound2t64，无 root 本地装：
apt-get download libnspr4 libnss3 libasound2t64
for d in *.deb; do dpkg -x "$d" root; done
export LD_LIBRARY_PATH=$PWD/root/usr/lib/x86_64-linux-gnu:$LD_LIBRARY_PATH
```

比特级无损核对：

```bash
ffmpeg -v error -i 浏览器产物.mka -map 0:a:0 -c copy -f streamhash -hash sha256 -
ffmpeg -v error -i 源视频        -map 0:a:0 -c copy -f streamhash -hash sha256 -
# 两个 hash 相同即无损（容器差异不计）
```

## 4. 踩坑记录（核心）

### 4.1 API 进程绝不能引入 CUDA
GPU Worker 用 `multiprocessing` **spawn** 启动，spawn 子进程会重新 import 主模块。因此 `worker.py` **顶层不 import torch/qwen_asr**，所有重依赖延迟到 `worker_main()` 内（此时已在子进程）。否则无 CUDA 的 API 进程会被污染。已用 `import server.main; 'torch' in sys.modules == False` 验证。

### 4.2 int8 加载必须 `device_map={"":0}`（不是 `"cuda:0"`）
`"cuda:0"` 触发 bitsandbytes 的 SCB 分发 bug（实测报告 §4.1）。全 GPU int8 用 `BitsAndBytesConfig(load_in_8bit=True)` + `device_map={"":0}`，对齐器固定 CPU float32。

### 4.3 `language=None`（自动判定）与验收 1 的张力
设计 §4.3 要求 `language=None` 以覆盖纯英文/中英混合（验收 8）；但实测参照是用 `language="Chinese"` 强制生成的。两者转写正文近乎一致（去标点 98.66%），但标点风格不同 → 断句不同 → cue 数不同（自动 26 vs 强制 47）。
- **解法**：新增 `VD_ASR_LANGUAGE` 配置，默认 `None`（自动），纯中文站点可设 `Chinese` 获得更密断句并贴近参照。既满足验收 8，又给出复现参照的开关。

### 4.4 启动恢复漏删中断任务音频
`startup_recover` 原本只把非终态任务标记 `failed(INTERRUPTED)`，未删其 `upload.bin`/`audio_16k.wav`，违反 FR-B7。
- **解法**：恢复时补 `cleanup_audio()`，单测验证音频删除、产物（items.json 等）保留。

### 4.5 WSL2 保留端口段：`bind` 失败但无进程监听
`8100` 无法绑定，报 `[Errno 98] address already in use`，但 `ss -ltn` 显示无人监听。这是 **Windows/Hyper-V 动态保留端口段**，WSL2 继承之，`bind()` 直接失败。且这些段会随重启重新生成（昨天 8200 可用、今天不可用即因隔夜重启）。
- **排查**：`python - <<'PY' ...socket.bind...` 扫一批端口即可看出哪些被保留。
- **解法**：换到可绑定端口（本项目用 **8200**）。若必须用某端口，Windows 管理员执行 `net stop winnat && net start winnat`，或 `netsh int ipv4 add excludedportrange protocol=tcp startport=<p> numberofports=1 store=persistent` 固定排除给自己。

### 4.5.1 WSL2 镜像网络（mirrored）下服务「监听 0.0.0.0 却访问不了」
服务端已绑 `0.0.0.0:8200`、WSL 内 `curl 127.0.0.1:8200` 返回 200，但**局域网别的设备打不开、连本机用 `192.168.x.x:8200` 也打不开**。表现具有强迷惑性，实为 mirrored 模式（`.wslconfig` 里 `networkingMode=mirrored`）的两层拦截：

1. **Hyper-V 防火墙默认拦入站**。mirrored + `firewall=true` 时，WSL 虚机的入站由 **Hyper-V 防火墙**管控，默认 `DefaultInboundAction=Block`，且无放行 8200 的规则 → 外部/本机都进不来。
   - 排查（Windows PowerShell，无需管理员）：
     ```powershell
     Get-NetFirewallHyperVVMSetting -PolicyStore ActiveStore `
       -Name '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' | Select DefaultInboundAction
     ```
     `{40E0…2E90}` 是 WSL 虚机固定的 VMCreatorId。
   - 解法（**管理员** PowerShell，二选一）：
     ```powershell
     # a) 只放行本项目端口（推荐，范围最小）
     New-NetFirewallHyperVRule -Name "WSL-video-digest-8200" -DisplayName "WSL video-digest 8200" `
       -Direction Inbound -VMCreatorId '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' `
       -Protocol TCP -LocalPorts 8200 -Action Allow
     # b) 一劳永逸放行 WSL 所有入站端口（仅在可信网络下用；公共 Wi-Fi 慎用）
     Set-NetFirewallHyperVVMSetting -Name '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -DefaultInboundAction Allow
     ```

2. **主机连自己的镜像 IP 的回环限制**（易被误判为「还没通」）。改完防火墙后，从 **Windows 主机自身**用 `192.168.x.x:8200` 或 `Test-NetConnection` 测**仍会超时/False**——这是 mirrored 模式「主机↔自己的镜像 IP」的回环限制，**证明不了外部通断**。真正可靠的判定：
   - 本机访问直接用 **`http://localhost:8200` / `http://127.0.0.1:8200`**（防火墙放行后即 200）。
   - 局域网别的设备用 `http://<主机IP>:8200`。
   - 若**一定要主机自己也能用 `192.168.x.x:8200` 这个地址**，在 `.wslconfig` 增开实验特性（注意 `hostAddressLoopback` 属 **`[experimental]`** 段，放进 `[wsl2]` 会报 `Unknown key`），然后 Windows 侧 `wsl --shutdown` 重启 WSL 生效：
     ```ini
     [wsl2]
     networkingMode=mirrored
     dnsTunneling=true
     firewall=true
     autoProxy=true

     [experimental]
     hostAddressLoopback=true
     ```

> 一句话小结：`0.0.0.0` 早已监听正常，访问不了几乎总是 **Hyper-V 防火墙拦入站** + **镜像 IP 主机回环**两件事，别去改监听地址。本机自测优先用 `localhost:8200`。

### 4.6 ffmpeg.wasm 自托管（UMD）最大的坑：worker 必须是"经典 worker"
症状递进（每一步都是真实报错）：

1. `Failed to construct 'Worker': Script at 'file:///vendor/ffmpeg/814.ffmpeg.js' cannot be accessed`
   - **根因**：`@ffmpeg/ffmpeg` UMD 用 `new URL(classWorkerURL, <硬编码 file:// 基址>)` 解析；传根相对路径 `/vendor/...` 会继承 `file://` 协议被浏览器拦截。
   - **解法**：`classWorkerURL/coreURL/wasmURL` 全传**绝对 http 地址**：`new URL(p, location.href).href`。

2. `Error: Cannot find module 'http://localhost:8200/vendor/ffmpeg/ffmpeg-core.js'`
   - **根因（关键）**：worker（`814.ffmpeg.js`）加载 core 的逻辑是先 `importScripts(coreURL)`，仅当 `importScripts` 不可用时才回退到 `r(454)(coreURL)`——而 `r(454)` 是 webpack 编译出的**死桩，永远抛 `Cannot find module`**。而官方在传了 `classWorkerURL` 时**硬编码**把 worker 造成 `{type:"module"}`（模块 worker 没有 `importScripts`），于是必然掉进死桩。
   - **解法**：给 vendored `ffmpeg.js` 打补丁，把 classWorker 的 `{type:"module"}` 改成 `{}`（经典 worker）。`814.ffmpeg.js` 是 UMD IIFE、无顶层 import/export、内部用 `importScripts`，作经典 worker 完全兼容。补丁前文件留 `ffmpeg.js.orig`，说明见 `web/vendor/ffmpeg/README.md`。
   - **连带**：经典 worker 走 `importScripts`，所以 core 必须用 **UMD** 构建（`ffmpeg-core.js`），**不能用 ESM**（ESM 走 `import()`，反而需要模块 worker——但那条路是死桩）。中途误换 ESM core 是弯路。

3. 控制台 `exports is not defined`
   - **根因**：`@ffmpeg/util` 的 UMD 在纯 `<script>` 下初始化报错；而本项目根本没用到它。
   - **解法**：移除未使用的 `util.js` 引用与文件。

4. 同一页面第二次提取报 `FS error`
   - **根因**：旧实现每次提取前都执行 `createDir("/in")`，但任务结束时的 `unmount("/in")` 只解除 WORKERFS 挂载，不会删除 `/in` 挂载点目录；第二次创建同名目录因此失败。
   - **解法**：ffmpeg worker 加载完成后只创建一次 `/in`，每次提取仅执行 `mount → exec/readFile → unmount`，挂载点在 worker 生命周期内复用。

**正确组合小结**：绝对 http URL + `classWorkerURL` 指向 `814.ffmpeg.js` + 打补丁成经典 worker + **UMD** core（`ffmpeg-core.js`/`.wasm`）。提取命令 `-map 0:a:0 -vn -c:a copy -f matroska /out.mka`，输入经 WORKERFS 挂载（不整体进 wasm 内存）。

### 4.7 浏览器缓存：改了服务端但用户仍报旧错
最隐蔽的坑。已把 `ffmpeg.js` 打好补丁、服务端也确认返回补丁版，但用户浏览器仍报 §4.6 第 2 条的错。
- **根因**：`index.html` 里 `app.js` 版本化了（`?v=`），但 `<script src="/vendor/ffmpeg/ffmpeg.js">` **没带版本号**；用户浏览器早先按启发式缓存了**旧的未打补丁** `ffmpeg.js`，同一 URL 被一直复用。app.js 是新的（走 UMD core 路径），但它 `ffmpeg.load()` 时用的是缓存里的旧 ffmpeg.js → 造出模块 worker → 死桩报错。
- **解法**：
  1. **所有**子资源 URL 带版本号：当前为 `ffmpeg.js?v=4`、`app.js?v=6`（新 URL 浏览器从未缓存，强制取新；资源变更时递增对应版本号）。
  2. HTML 文档一律 `Cache-Control: no-store`（页面永不复用缓存，保证总能拿到引用最新 `?v=` 的页面）；其它静态资源 `no-cache`（带 ETag，未变更回 304，变更即取新）。
- **用户侧一次性动作**：首次仍需一次绕过缓存的加载拿到新 `index.html`——**Ctrl+Shift+R 硬刷新**或**无痕窗口**。之后 `no-store` 保证长期生效。

### 4.8 长音频转写 `WORKER_CRASHED`：4GB 卡上密集块越界 → 驱动级 OOM 硬退出
一条 95min 音频（`audio_duration_sec=5714`）转写约 7.5min 后任务失败 `WORKER_CRASHED`，`task.log` 只停在 `preprocessing done`。而 10min 样本一直正常。
- **定位**：独立复现脚本逐块打印 `torch.cuda.memory_reserved/allocated`。常驻 int8 模型基线约 **3.07GB reserved**（4GB 卡仅 ~1GB 余量）；单块峰值**内容相关**——同一 30min 影片里不同块 `peak_resv` 在 3.07↔3.26GB 跳动（语速密集、生成 token 多的块更高）。把 `chunk_sec` 强行调到 180s 复现越界，**首块**即抛：
  ```
  RuntimeError: CUDA driver error: out of memory   # 注意不是 torch.cuda.OutOfMemoryError！
  ```
- **两个根因**：
  1. **越界形态被漏判**。4GB 卡越界抛的是**普通 `RuntimeError`**（"CUDA driver error: out of memory"），而 `asr.transcribe` 的自愈只 `except torch.cuda.OutOfMemoryError`——此环境几乎走不到，等于**死代码**，OOM 从不自愈。
  2. **驱动级 OOM 可损坏 CUDA 上下文**，使 Worker 子进程**硬退出**（非抛异常）→ 调度器 `is_alive()==False` → 标记 `WORKER_CRASHED`（故 `except Exception` 的 INTERNAL 路径也接不到）。默认 `chunk_sec=45` 时，原文件某个密集块的瞬时分配越过 4GB 触发之。
- **解法（预防为主 + 兜底收口）**：
  1. `config.py` 默认 `chunk_sec` **45 → 30**：收窄单块音频编码器激活与每块 token 上限，实测同片 `alloc` 峰值 **2.87GB → 2.48GB**（多留 ~0.4GB 余量）。显存更大的卡可 `VD_CHUNK_SEC` 调高。
  2. `asr._is_oom()` 按**异常消息**兜底识别显存不足（含普通 `RuntimeError`），自愈 `except` 改为「非 OOM 才 reraise」；`worker._classify` 同样按消息把这类错误归为 `GPU_OOM`。这样即便极端文件仍越界，也是**干净的 `GPU_OOM`（可重试提示）**而非神秘的 `WORKER_CRASHED`。
- **运行备注**：Worker 子进程 stderr 走父进程 stdout；前台起（`python -m server.main`）时崩溃栈未落盘，排查困难。用 `./run.sh --bg`（日志 `server.log`）起，崩溃原因可追。

### 4.9 GPU ASR / CPU 对齐流水线：不加显存隐藏对齐耗时
qwen-asr 0.0.6 的 `transcribe()` 先对所有块执行 `_infer_asr()`，再对非静音块执行 `forced_aligner.align()`；因此 GPU 解码时 CPU 对齐器空闲，进入对齐后 GPU 又空闲。本项目固定 `max_inference_batch_size=1`，可等价重排为：

```text
主线程/GPU:  ASR 0 ─ ASR 1 ─ ASR 2 ─ ASR 3
CPU 线程:           ALIGN 0 ─ ALIGN 1 ─ ALIGN 2 ─ ALIGN 3
```

- `asr._transcribe_pipelined()` 仍复用上游的音频归一化、静音切块、语言解析、时间偏移与合并方法；仅重排逐块调用，不自行切音频或重写时间戳算法。
- 只有一个 CPU 对齐线程、至多一个 Future 在途。主线程完成当前 ASR 后汇合上一块对齐再投递当前块，形成容量 1 背压；长音频不会积压待对齐音频，异常时最多等待当前一次 CPU 调用。
- ASR 模型/processor 只由主线程使用，对齐模型/processor 只由 CPU 线程使用；进度和结果合并也只在主线程执行，避免共享状态竞争。
- OOM 仍由外层清缓存后整段重试一次；每次重试重新分块并重置进度。

**真实 GPU A/B（RTX 3050 Laptop 4GB，120s 中文语音，30s×4 块，同一模型实例）**：

| 路径 | 耗时 | 峰值分配显存 | 正文/语言/570 个时间戳 |
|---|---:|---:|---|
| qwen-asr 原串行 | 119.366s | 2.680GB | 基线 |
| 项目流水线 | **84.337s** | **2.626GB** | **完全一致** |

计时钩子检测到 3 组相邻块 ASR/对齐区间真实重叠、运行于两个线程；节省 35.029s，提速 1.415x。单元测试另覆盖并发时序、时间偏移/顺序合并、静音跳过和对齐异常传播。

### 4.10 长视频字幕稀疏：固定标点表与对齐器清洗规则不一致

157.6 分钟样本的旧字幕只有 633 条、9,139 个对齐字符，看起来从约 23 分钟起
持续漂移并漏掉后半段。检查转写阶段保留的 `items.json` 后确认模型实际已输出
42,319 字正文、37,784 个对齐字符，最后一个 token 在 `9455.763s`，长视频转写
和分块偏移均正常。

- **根因**：`layout.align_chars()` 用手写 `PUNCT` 集合判断哪些正文字符不会出现
  在对齐 token 中。集合没有包含 ASCII `.`；正文第一次出现 `A.I.` 时，旧算法
  把点号当待匹配字符，并为寻找它向前消费最多 3 个真实 token 字符。之后正文与
  token 游标永久错位，大部分字符拿不到时间戳，断句时被静默丢弃。
- **修复**：按 Qwen `Qwen3ForceAlignProcessor.clean_token()` 的实际契约处理字符：
  只保留 Unicode 字母、数字和英文撇号，其余字符保留在显示正文中但不消费时间
  token。归一化正文与 token 不完全相等时立即失败，不再静默生成残缺字幕。
- **边界处理**：强制对齐器偶尔给相邻短语同一起点和零长度时间点。排版层现在先
  合并这种无法独立显示的 cue，再执行最短时长和消重叠逻辑，避免负时长 SRT。

用原始 `items.json` 重建（无需重跑模型）后得到 2,750 条 cue、37,784 个对齐
字符，正文保留率 100%，末条结束于 `9456.203s`，非法时间段为 0。回归测试覆盖
`A.I.`、斜杠、英文撇号、正文/token 契约异常及同起点 cue。

### 4.11 多模型接入：把模型差异收敛在 backend 契约内

最初 Qwen 的加载、分块、推理和对齐集中在 `pipeline/asr.py`。直接继续堆模型分支会让
Worker、后处理和 API 都感知实现细节，因此现在由 `create_backend(cfg)` 延迟构造：

```text
worker.py -> AsrBackend.transcribe(...)
              |- QwenBackend
              |- FireRedBackend
              `- FunAsrBackend (experimental)
                         |
                         v
        {text, language, items, backend, model_id, warnings}
```

- 重依赖仍只在 Worker 内导入，API 进程保持 torch-free。
- `status.json` 在任务创建时记录 `asr_backend/model_id`，切换部署配置后历史产物仍可追溯。
- `/api/health` 以 ready Event 判断模型是否真正加载；缺依赖、模型目录错误或源码版本错误会返回 `startup_error`，不会只因进程存活就报 ready。
- `run.sh` 必须按当前 backend 检查解释器依赖。旧脚本只检测 `qwen_asr`，即使设置 FunASR 也可能错误选中 Qwen 环境；现在按 `VD_ASR_BACKEND` 分别检查。

### 4.12 输出校验必须放在 ASR 与排版之间

不同模型的时间戳字段、标点 token 和语言元数据不同，但 `layout` 只应接收一个可靠
契约。`backends/base.py::validate_asr_output()` 在每个 backend 返回前统一检查：

1. `text` 为字符串、`items` 为列表，item 含 `t/s/e`；
2. 只保留 Unicode 字母、数字和英文撇号后，正文与全部 timed token 必须完全一致；
3. 时间为有限数、整体单调，且在 `[-0.001, audio_duration+0.25]` 容差内；
4. 任一不满足即抛 `AsrOutputError`，Worker 记录 `ASR_OUTPUT_MISMATCH`，不生成 SRT。

这道守门同时覆盖 Qwen、FireRed 和 FunASR。它把 §4.10 的“排版阶段静默丢字”从
事后修复变为模型输出落盘前失败，代价是上游格式变更会显式暴露，符合预期。

### 4.13 上下文不是一个跨模型同义参数

公共入口使用 `VD_ASR_CONTEXT`，但三个 backend 的语义必须明确区分：

- Qwen：去除首尾空白后，完整字符串传给每个 `_infer_asr` 的 context 参数；
- FunASR：按中英文逗号、分号和换行拆分，去空、按首次出现顺序去重，作为 `hotwords`；
- FireRedASR2-AED：当前 API 没有相同能力。任务仍执行，但在 `items.json.warnings` 写入 `ASR_CONTEXT_UNSUPPORTED`，不能假装热词已生效。

同理，`VD_ASR_LANGUAGE` 只对 Qwen/FunASR 透传；FireRed 配置非空直接失败。FireRed
自动模式写 `Unknown`，因为当前调用路径没有可靠 LID 输出，不能用配置或默认值伪造。

### 4.14 低能量边界不是 VAD

FireRed/FunASR 原来每 30 秒硬切，容易在词中间断开。公共 `iter_wav_chunks()` 现在
在目标切点前默认 5 秒范围搜索 100ms 滚动窗口的最低绝对振幅位置；同能量时选最接近
目标点的位置。实现坚持三条不变量：

- 所有 offset 由 16 kHz PCM frame 计算，块首尾连续，不丢不重；
- 边界只能向前移动，因此块长永不超过 `VD_CHUNK_SEC`；
- 只改变分块边界，不判断“有人声”、不删除静音，也不增加 padding，所以不能称为 VAD。

FireRed 的异常递归子块仍按精确二分，不再次做边界搜索，避免重试树不可预测。Qwen
继续复用 qwen-asr 自身分块，未改用这套公共切块。

### 4.15 第三模型试验：可运行不等于可替换默认模型

Fun-ASR-Nano-2512 已通过 180 秒 CUDA 试验：RTF 0.122，峰值分配显存 3.755GB，
能输出原生标点和字符时间戳，并适配为公共 items 契约。它的速度接近 FireRed，但在
4GB RTX 3050 上仅剩很小余量；一次短样本也不能回答领域词 CER、小时级稳定性和许可
适用性。因此代码保留 `funasr` backend，产品定位明确为 experimental，默认值不变。

完整决策、依赖和准入门槛见 `docs/ASR三模型接入评审与试验补充.md`。

## 6. 方法论教训

- **前端 bug 必须用真实浏览器端到端复现后再下结论**。前几轮我用"全新浏览器"跑 Playwright，一直 PASS，恰恰**掩盖了用户的缓存问题**；改用**持久化 profile** 先复现"中毒缓存"态（Phase1 完整复现用户报错），再验证修复（Phase2 + 真实 `/` 全流程到 DONE），才算真正验证。
- 不要凭源码猜浏览器 Worker/缓存行为——它们有大量运行时特异性（模块/经典 worker、`file://` 解析、启发式缓存）。
- 无 root 也能装 headless 浏览器依赖（`apt-get download` + `dpkg -x` + `LD_LIBRARY_PATH`）。

## 8. 增量特性：历史任务列表（v1.1）

**动机**：任务成功后 task_id 只写在地址栏（`?task=`），没存 localStorage、也没有列任务的接口。用户若把标签页整个关掉、重开一个干净首页，服务端任务其实已跑完、产物也在磁盘上，但前端没有线索找回。补一个历史列表解决"重开即找回"。

### 8.1 设计取舍：服务端目录扫描，而非浏览器 localStorage
真相在磁盘 `status.json`（"文件系统即状态"）。服务端 `GET /api/tasks` 扫描任务目录返回摘要，天然对**清缓存 / 换浏览器 / 换设备**鲁棒；localStorage 方案则要在前端再维护一份可能与磁盘不一致的索引，且清缓存即丢。对应需求 FR-F8、设计 D8。

### 8.2 落地
- 后端 `store.list_tasks()`：扫描 `data/tasks/*/status.json`，取轻量字段，按 `created_at` 倒序（同为 `+08:00` ISO，字典序即时间序），默认跳过 `deleted` 墓碑，上限 200。
- 后端 `GET /api/tasks?include_deleted=`（`main.py`）：`queued` 任务附实时 `queue_position`，与 `GET /api/tasks/{id}` 分别匹配集合和单任务路径。
- 前端 `app.js`：`loadHistory()` 拉取渲染，`openTask(id)` 复用 `?task=` 恢复路径，条目带状态徽章 / 时间 / 时长 / 删除；进入首页与点「处理新文件」时刷新。样式见 `style.css` 的 `.hist-*`。

### 8.3 一处前端联调坑：异步重渲染导致节点失效
Playwright 用例里先 `page.$$('.hist-del')` 抓到按钮句柄，再点击——但 `loadHistory()` 是异步 `fetch` 后 `list.textContent=""` 重建列表，抓到的旧句柄已从 DOM 脱离，报 `Element is not attached to the DOM / not stable`。
- **解法**：改用会在点击时**重新解析**的 locator（`page.locator('.hist-del').last().click()`），并用 `waitForFunction` 等列表条数稳定后再断言。这是测试写法问题，非功能缺陷——但同样印证"前端要用真实浏览器跑通、别靠句柄快照猜 DOM"（呼应 §6）。

### 8.4 真实浏览器验证（Playwright + 持久化 profile）
| 检查 | 结果 |
